# 開發任務流程

適用於：新增功能、新模組、既有功能的行為調整、架構調整、重構、code review 後的改善。

核心是把一件開發工作拆給四個獨立 subagent 依序完成：規劃 → 開發 → 驗證 → 資安檢測。每個 subagent 都是全新的 context，看不到你跟使用者的對話，**所有背景都要寫進 prompt 裡**，不能假設它「應該知道」。

---

## Step 0：先建立共同背景（主流程自己做，不外包）

在開第一個 subagent 之前，先花幾分鐘把後面每一步都會用到的東西備齊，否則四個 subagent 會各自用不同的假設工作：

1. **需求本身**：要做什麼、範圍到哪裡、什麼**不**在這次範圍內。使用者講得含糊時，優先用專案現況推斷；只有在不同解讀會導致做出完全不同的東西時，才回頭問使用者。
2. **專案慣例**：讀 `CLAUDE.md`、`README`、相近功能的既有程式碼，確認語言/框架、命名規則、分層結構、既有的錯誤處理與記錄方式。能引用具體檔案路徑就引用，讓 subagent 直接去讀，不要轉述。
3. **驗證方式**：這個專案怎麼 build、怎麼跑測試（`dotnet build`、`npm test`、`pytest`⋯）。有寫在文件或 `package.json` scripts 就照抄，不要用猜的指令——跑錯指令產生的失敗訊息只會誤導驗證 subagent。若專案沒有自動化測試，就明確講清楚，讓驗證 subagent 改做靜態審查＋產出人工驗證步驟，而不是硬跑不存在的指令。
4. **重試上限**：預設最多 3 輪「開發 ⇄ 驗證」來回。到達上限仍未通過，就停下來如實回報現況，讓使用者決定要不要繼續。

任務很小（改一行文字、調一個 timeout 數值）時，直接做完並簡單說明即可，不必為了套流程而小題大作。這套流程是為有一定複雜度的工作設計的。

---

## Step 1：規劃 Subagent

**agent**：`subagent_type: senior-engineer-planner`（定義在 `.claude/agents/senior-engineer-planner.md`，唯讀工具）。環境裡沒有這個定義時退而求其次用 `general-purpose`，並在 prompt 裡明確限制它「只分析與規劃，不要動手改任何檔案」。

**prompt 至少包含**：完整需求敘述、Step 0 蒐集到的專案慣例與檔案路徑、明確的邊界（什麼不做）。

**要求它輸出**：

- 這次要達成的行為，用可驗收的方式描述（做完之後「什麼情況下會發生什麼」）
- 具體實作步驟，逐步可執行
- **要新增/修改哪些檔案**，各自要改什麼
- 預期風險：會動到哪些既有行為、有沒有共用元件被影響、資料相容性或遷移問題
- 驗收標準：驗證 subagent 該檢查什麼、該跑什麼

規劃是後面三步的共同依據，所以「模稜兩可的計畫」比「錯的計畫」更難處理——錯的計畫驗證得出來，模糊的計畫會讓每個 subagent 各自填空。收到計畫後自己讀一遍，覺得含糊就要求補齊再往下走。

---

## Step 2：開發 Subagent

**agent**：`subagent_type: senior-engineer-developer`（沒有這個定義時用 `general-purpose`）。

**prompt 至少包含**：規劃 subagent 的完整計畫（原文貼上，不要摘要成幾句話）、專案慣例、要遵守的檔案路徑。

**明確告訴它**：把實作做對、做乾淨，遵循既有慣例；**不必**自己判斷測試是否全過——驗證是下一步另一個 agent 的職責。完成後用簡短文字說明改了哪些檔案、為什麼這樣改（給後面的 subagent 當背景，但它們仍須自行查證，不能只採信這份自述）。

**必須完全依照規格執行，規格不明確處不准自行猜測補完**：prompt 裡要明講——

- 規格文件裡明確寫出的行為（格式、欄位、順序、文字內容），要逐字對照實作，不能用「語意差不多」的替代方案（例如規格要求顯示代碼，不能因為系統裡剛好有名稱欄位就改顯示名稱）。
- 規格本身標示「待確認」「TODO」，或規格含糊到無法唯一決定實作方式時，**不要自己猜一個值或邏輯放進去**——只能在對應位置寫 `// TODO: <規格待確認事項，需與誰／哪個管道確認>` 的註解，並讓這部分維持未實作或維持最小可編譯的空狀態，不能補一個「看起來合理」的固定值或行為冒充已完成。
- 完成後的自述裡，要把這次「因規格不明確而只寫 TODO、未實作」的項目全部列出來，不能省略，讓後面驗證與完工報告都看得到。

這一步用 `run_in_background: false`，因為後面每一步都依賴它的結果。

---

## Step 3：驗證 Subagent

**agent**：`subagent_type: senior-engineer-verifier`（沒有這個定義時用 `general-purpose`）。**不要**延續開發 subagent 的 session——獨立性正是這一步的價值。

**prompt 至少包含**：原始需求與規劃內容（讓它能判斷「有沒有做到需求」，而不只是「程式碼看起來乾不乾淨」）、實際改動的檔案清單或 `git diff`（讓它自己去讀）、build/test 指令。

**要求它**：

- **實際執行** build/test，不要只憑讀程式碼猜測結果
- 檢查既有功能有沒有被破壞（相關的回歸測試、共用元件的其他呼叫端）
- 若專案沒有自動化測試，改做靜態審查，並產出可照著操作的人工驗證步驟
- 輸出 `PASS` / `FAIL`；FAIL 時給出「檔案 + 行號 + 問題描述」的具體清單，要讓開發 subagent 不用回頭問就能直接動手

**FAIL 時**：把問題清單原封不動轉給新一輪的開發 subagent（全新 session，附上原始需求、計畫、問題清單），改完再回到 Step 3。輪數 +1，到達上限就停下來回報。

---

## Step 4：資安檢測 Subagent

**agent**：`subagent_type: senior-engineer-security`（唯讀工具；沒有這個定義時用 `general-purpose`，並限制它「只檢查與描述風險，不要動手修」）。

**prompt 至少包含**：改動的檔案清單/diff、這個功能會接觸到什麼資料與外部輸入、專案既有的權限或驗證機制在哪裡。

**至少檢查**：

- 硬編碼的密鑰、密碼、token、連線字串，或被寫進 log 的敏感資料
- 注入類漏洞：SQL/命令/路徑穿越/範本注入，以及輸出未跳脫造成的 XSS
- 輸入驗證與邊界檢查是否缺漏
- 權限與驗證：新增的進入點有沒有沿用既有的授權檢查，會不會被繞過
- 新引入的相依套件是否必要、來源是否可信、有沒有已知漏洞
- 錯誤訊息是否洩漏內部結構

**要求它輸出**：風險清單（嚴重度 + 位置 + 為什麼是風險 + 建議修法），以及「檢查了哪些面向、哪些確認無虞」——只寫「沒發現問題」而不說檢查範圍的結論沒有參考價值。

**發現高風險時**：回到 Step 2 修掉再重跑 Step 3、Step 4。低風險或屬於既有設計的問題，寫進完工報告的後續建議，不要擅自擴大這次的改動範圍。

---

## Step 5：完工報告

四步走完後，主流程整理出一份報告給使用者。這份報告是使用者唯一看得到的東西——subagent 的過程他們看不到，所以資訊要自足，不要只寫「已完成」。

```markdown
## 完工報告

### 這次做了什麼
- <一句話總結>
- 改動檔案：
  - `path/to/file.ext` — <改了什麼>

### 為什麼這樣做
<對應規劃 subagent 的判斷：為什麼選這個做法、有沒有考慮過其他方案、取捨在哪裡>

### 規格待確認 / 未實作項目
- <因規格不明確或標示待確認而只留 TODO 註解、未實作的項目；沒有就寫「無」>

### 驗證結果
- 執行指令：`<實際跑的指令>`
- 結果：<通過/失敗數量，關鍵輸出>
- 涵蓋範圍：<測了什麼；沒測到什麼>

### 資安檢測結果
- 檢查面向：<列出實際檢查的項目>
- 發現：<風險清單，或明確寫「未發現新增風險」>

### 後續建議
- <可選：技術債、範圍外的問題、建議人工確認的地方>
```

沒做到的部分要照實寫出來，不要用模糊字眼帶過。驗證沒過或資安有未修的風險，也要寫進報告，讓使用者自己判斷要不要繼續。
