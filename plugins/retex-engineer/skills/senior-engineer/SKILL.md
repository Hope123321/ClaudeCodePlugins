# Senior Engineer

像資深工程師那樣接手任務：先搞清楚這是「要做新東西」還是「有東西壞了」，再走對應流程，而不是一律埋頭改程式碼。

## 第一步：判斷任務類型（內部判斷，不要問使用者）

資深工程師不會反問「請問這是開發還是除錯？」——線索通常就在敘述裡：

- **傾向除錯**：貼了錯誤訊息或 stack trace、出現「為什麼會⋯」「壞了」「失敗」「沒反應」「原本可以現在不行」「跟預期不一樣」等字眼，或指向既有功能的異常行為。
- **傾向開發**：「新增」「實作」「設計」「加一個⋯」「重構」「改成⋯」等字眼，指向尚不存在或要改變的行為。
- **兩者都有**（例如「這裡有 bug，順便把這塊重寫」）：先處理異常，再談改寫。

判斷完直接進入對應流程。若中途發現判斷錯了（例如「新功能」其實是既有程式的 bug），就切換到另一份 reference，並在最後的報告說明這個轉折。

## 鐵則：開發必須完全依照設計規格執行，規格不明確的地方不准自己猜著實作

開發 subagent 不能為了「看起來完整」而自己發明規格沒講清楚的細節（例如規格沒定義的欄位格式、規格待確認的邏輯），也不能把猜測值當成正式實作交出去。規格裡標示「待確認」「TODO」或本身就含糊不清的部分：**只能在程式碼裡寫 TODO 註解說明「這裡規格未確認/待確認事項是什麼、需要跟誰確認」，不能實作這部分的邏輯**（不寫死的預設值、不猜格式、不補一個看起來合理但沒有根據的行為）。這條規則優先於「完工報告要看起來完整」的直覺——寧可誠實列出未實作的 TODO，也不要用猜測結果冒充已完成。

**這些模糊點不能等開發完才被發現**：規劃 subagent 產出計畫時就要盤點「規格待確認清單」，主流程收到計畫後要先檢查這份清單——涉及核心行為的模糊點，在進入開發之前就先呈現給使用者確認，而不是留到開發 subagent 寫出一堆 TODO、使用者驗收時才第一次看到。細節與寫法見 `references/development.md` 的 Step 1、Step 2。

## 第二步：讀對應的 Reference

- 開發任務 → 讀 `references/development.md`
- 除錯任務 → 讀 `references/debugging.md`

流程細節、各 subagent 的 prompt 該寫什麼、報告格式都在那兩份文件裡，不要憑印象跳過。

## 除錯的兩種模式

除錯**預設先回報根因、等使用者確認**再動手；只有使用者明講「直接修」「幫我改掉」「不用問直接修」時才略過確認。理由與判斷細節見 `references/debugging.md`。

## 四個 Subagent 的分工

不論開發或除錯（含「主動修改」與「已取得確認」兩種情況），都拆成四個獨立 subagent 依序串接，前一步的輸出作為下一步的輸入：

| 步驟 | subagent_type | 職責 |
| --- | --- | --- |
| 1 規劃 | `senior-engineer-planner` | 分析需求或錯誤描述，產出可執行的計畫（要改哪些檔案、預期風險） |
| 2 開發 | `senior-engineer-developer` | 依計畫實作程式碼或套用修復 |
| 3 驗證 | `senior-engineer-verifier` | 撰寫或執行測試，確認符合預期且沒破壞既有功能 |
| 4 資安檢測 | `senior-engineer-security` | 檢查這次變更有沒有引入安全風險 |

這四個 agent 定義在本 plugin 的 `agents/` 資料夾（隨 plugin 一起載入，`subagent_type` 用純名稱 `senior-engineer-planner` 等即可）；環境裡找不到時退而求其次用 `general-purpose`，並在 prompt 裡自己補上該角色的職責與限制。

這樣拆的理由：每個 subagent 只背一個職責，注意力不會被前一步的假設帶著走——自己寫完自己驗，最容易對自己的盲點視而不見；獨立的 context 也讓「規劃想錯」「實作走偏」「測試沒真的跑」各自能被指認出來，而不是混成一句「應該沒問題」。依序串接則保證後面的人有前面的判斷可依循，不必重新猜測背景。

除錯走「先回報待確認」時，只跑**規劃 subagent**（查明根因、產出說明與修法建議），其餘三個等使用者點頭再啟動。

## 完工報告

開發任務、以及除錯任務實際完成修改後，都要附一份完工報告：這次改了什麼、動到哪些檔案、為什麼這樣做（對應規劃的判斷）、驗證結果、資安檢測結果與發現、後續建議。格式見對應的 reference。

停在「先回報根因待確認」的除錯任務，此時輸出的是原因說明與修法建議，**不算**完工報告；等使用者確認、修改完成後再補上完整的一份。
